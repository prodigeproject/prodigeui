# Quiet-capability fresh benchmark — 22 August 2026

## The question

The previous design-engineering comparison showed a real gain in action state,
context, and recovery. It also exposed a regression: the tuned side could make
every capability visible at once and thereby lose the user-approved baseline's
calm, focal clarity, and room to breathe.

This fresh fixture asks a narrower question:

> Can the current rules retain the baseline's quiet first viewport while making
> the full product state available only when it changes the person's decision?

| Lane | Source |
| --- | --- |
| Baseline | `43f629e` — user-approved market-calibrated baseline in the v3.0.8 lineage |
| Quiet capability | Current working tree after the Exposure Map and first-viewport-budget tuning |

The four pairs are independently authored from the same fixed brief. They do
not share a page shell, CSS file, or benchmark generator. When a product photo
is relevant, both sides reuse the same local file so the review attributes the
difference to information exposure, type, hierarchy, state, and interaction—not
to a more flattering image.

## Evaluation contract

- The **baseline is not a straw man**. Its composition, evidence, and initial
  decision should remain coherent even though its action paths are static.
- The **quiet lane is not allowed to hide functionality**. It must contain one
  runnable action, a visible acknowledgement, a changed/success state, a
  recovery route, focus treatment, and reduced-motion behavior.
- The quiet lane may defer a state, explanation, or helper only when that fact
  is not necessary for orientation, safety, cost, eligibility, or the immediate
  commitment.
- Review calm and completeness as separate scores. A busier page cannot win
  merely because it has more implemented states; a static hero cannot win merely
  because it looks serene.

## Known limits

- These are one fresh pair per product, not a statistical model evaluation.
- Action results are local simulations, not live commerce, healthcare, release,
  or booking systems.
- System-font plans are deliberate; exact rendering remains platform-dependent.
- Desktop is rendered in the local browser. Compact behavior is implemented and
  inspected in code; the scorecard must not claim an emulated-device pass unless
  it is actually rendered.

See `SCORECARD.md` for the final result and any regression that prevents
promotion.
